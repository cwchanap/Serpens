# HPA-718 Feature-ownership Redesign Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (pre-authorized) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reduce the current 2,952-line game page toward ~1,200 through cohesive feature ownership without changing player behavior or controller authority.

**Architecture:** Per-route-instance Svelte factories own temporary feature state, while existing hosts acquire their feature read models and command adapters. The page remains the controller/composition root and owns synchronous cross-feature resets, alert/guidance orchestration and read-only overlay policy. No aggregate route proxy, context provider or shadow game store.

**Tech Stack:** TypeScript, Svelte 5 forced runes, SvelteKit, Bun, Vitest browser/node projects, Playwright, existing Phaser snapshot hosts.

**Spec:** `docs/superpowers/specs/2026-11-04-hpa-718-ownership-redesign.md` (read in full). Original unchanged invariants: `docs/superpowers/specs/2026-11-04-hpa-718-route-modules-design.md`. This plan replaces the remaining extraction/final-audit stages of `docs/superpowers/plans/2026-11-04-hpa-718-route-modules.md`; do not redo completed controller/policy work.

Root retains controller projections, accepted activity, identity comparison, synchronous ordered resets, alert/guidance routing, overlay projection, shell flags and screen/layout composition.

- Commands use feature-only `Pick<GameRouteController, …>` ports and `commands.method(...)`; preserve method binding, original promises/results, `null` preflight and `unavailable` versus `busy`. No `getState`, repository, global store/bus/provider, generic dispatch/actions bag or sibling-owner registry.

- Nine **serial** vertical implementation tasks below, each independently testable/committable using named callbacks to still-page-owned siblings. They are not parallel edits to the shared page. Final audit follows Task 9, not a tenth catch-all extraction.

## Review Focus

These risks must be tested in their owning tasks, not dismissed because the change is called a refactor:

1. **Deferred/stale async completion:** feedback appears at the original time; stale review/confirmation cannot clear a newer UI or claim success (Tasks 1–3, 5).
2. **Live inputs without remount:** changed game/city/locale/permission updates getters while result identity, focus and durable context retain intended lifetimes (Tasks 2, 4–6, 9).
3. **Non-day changes during a running deadline:** game replacement/pending command must not postpone or stall auto-tick (Task 7 plus Task 2 adoption integration).
4. **One physical input across event phases:** review/dialog/canvas ownership prevents a second page dismissal or waypoint pop (Tasks 3, 8).
5. **Partial cleanup and conditional mounts:** successful load, scenario adoption, planner handoff, hide and user close are distinct; pending read-only inspection and visited canvases remain usable (Tasks 1, 4–6).

### Root protocols that every task must preserve

Keep these named route functions and order, rewriting bodies to call new named owners as tasks land:

- `synchronizeControllerState`: assign controller projections; clear scenario evidence on sandbox synchronization; compare `playMode/runId/status/scenarioRunSyncEpoch`; synchronously call `resetTransientViewState` only for existing identity/epoch changes. Controller accepted-change observer alone updates `mapActivity`.
- `resetTransientViewState`: clear retail/industry/world selection, selected logistics and its focus, preset/source focus, store detail, hide build/advisor, pause, close menu/alerts, hide management, clear finance focus, cancel placement/review. Do not reset visited maps, durable planner context or scenario UI identity/expansion by convenience.

- Root overlay snapshot reads owners, never writes duplicate flags. Root `closeOverlay`/`clearSelection` switches retain contextual exceptions and call named operations.
